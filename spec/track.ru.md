# Трек: конфигурация процесса

Статус: **ЧЕРНОВИК v2.1**, 2026-09-24. Спецификация: [`process-configuration.ru.md`](process-configuration.ru.md). Роадмап: `wiki/roadmap/ecosystem-roadmap.md`, линия конфигурации процесса (она заменяет прежний трек плейбуков PB0–PB4 из `skill-project-management/.specs/drafts/playbooks-track.md`). Прогоны опровергателя: [`../reviews/2026-09-24-refuter-v0.md`](../reviews/2026-09-24-refuter-v0.md) по v1 и [`../reviews/2026-09-24-refuter-v1.md`](../reviews/2026-09-24-refuter-v1.md) по v2.

## Зачем

Структура доски — типы элементов, статусы, цикл продюсер–ревьюер, роли — это код на Go внутри task-board. Операторы решили 2026-09-24, что вынести её во внешнюю конфигурацию уровня проекта, которую обрабатывает отдельный модуль, — первый приоритет: так любой сможет описать свой процесс, доска станет полезной за пределами разработки ПО, а следующая доска переиспользует модуль, а не перепишет его. Текущая доска остаётся на поддержке; новые возможности приходят модулями, подключёнными через тонкие швы.

## Демо-плейбуки

Каждое демо берёт нарочно сырой вход и проводит его через свой плейбук под одним оркестратором. Цепочки показывают, как результат одного плейбука становится входом другого.

1. `dev-cycle` — сегодняшний процесс поставки, приведённый в порядок, с инвариантами доставки. После PC1.
2. `bug-hunt` → `dev-cycle` — доказанная находка передаётся процессу исправления на той же доске. После PC1.
3. `scrum` поверх `dev-cycle` — каденция в композиции поверх поставки: спринты держат story через связи, поля оценок делегирует привязка слота. После PC1.
4. Работа кафе с бухгалтерией — инвентаризация → закупка → учёт: люди, инструмент, таймеры, повторения, подписанные события, передача работы с возвращаемым результатом. После PC3 и поправки к waggle.
5. Инцидент → разбор инцидента → исправление в `dev-cycle`.
6. Патент — исследование → черновик → опровергатель → подача заявки.
7. Агентство — лид → оценка → проект (`dev-cycle`) → счёт.

## Зависимости

- **Curator:** вывести Skillfile схемы 2 из-под флага; `dependencies.skills` получает выбор `directory`, чтобы оркестратор мог зависеть от провайдера инструмента в своём же репозитории (спецификация §8.3). Зависимости в режиме `runtime`, суженные до команд, уже есть (curator-spec core §4.4).
- **Выбор агента** (`skill-project-management/.specs/drafts/agent-selection.md`): спецификация вносит поправки в его §3 (словарь и написание потребностей), §7 (допуск без файла оператора) и §8 (временное ослабление), а также в LP D9 (профили запуска) для случая без файла оператора; `Playbook.json` заменяет его закоммиченный проектный слой для потребностей ролей, допуска, политики данных и снятия требований.
- **waggle:** подписи одобряющих, предложения передачи работы и аренды областей, которые уже есть; и **поправка** для владельца спецификации waggle (спецификация §17, H7): класс для одобрений доски и подписанных переходов, класс событий с истечением срока и дедупликацией, вид сервисного принципала для мостов событий, тип `coord`, который возвращает результат передачи работы, и проверка пользователя, доступная политике доски. Она нужна PC3 и демо кафе; демо после PC1 она не нужна.
- **Планировщик:** `task-board tick` нуждается в периодическом вызове: возможность, которой у хоста сессий пока нет, или задокументированная запись launchd, таймера systemd или cron (спецификация §6.9). PC3.
- **Хранилище аренд:** собственная аренда доски на одной машине; хранилище аренд waggle (NATS JetStream KV, веха CM2) для доски, общей для нескольких машин. До CM2 общая доска запускает tick только на одной машине.
- **Хост сессий:** помечает сессии под хостом, чтобы ядро отличало сессии агентов от людей, и может держать периодический tick и исполнитель инструментов.
- **task-board:** шов для PC1, швы доставки поверх сегодняшних команд, локальная передача работы и журнал целей (и `rejected`, если журнал его примет).

## Риски

- Точное воспроизведение сегодняшней разрешающей модели статусов: у ядра нет таблицы переходов, и несколько проверок зависят от контекста прогона (запущенный прогон, собственный элемент, ручное перемещение). PC1 может принять задокументированные отличия вместо тождества; их перечисляет §14 спецификации.
- Полномочия сильны ровно настолько, насколько сильны сигнал об акторе и закреплённая ревизия: пока сессии под хостом не помечены, а действия не подписаны, отказы для прогонов агентов — лишь страховка; проект без git или проект, чьи вливания не проходят ревью, ослабляет закреплённую ревизию.
- Подписи показывают, что действовал человек, только когда несут проверку пользователя; ключи, которые не могут её нести (сегодня это ключи Secure Enclave), защищают сам ключ, но не присутствие, и это должен решить вопрос H7.
- Два источника правды для ролей во время миграции (`.roles`, `~/.roles`, установленные скиллы): порядок поиска в PC2 должен быть явным и записываться в журнал.
- PC1 растёт на швы доставки и локальную передачу работы, которые нужны ранним демо; каждый шов должен оставаться тонким адаптером поверх сегодняшних команд.
- Схема меняется до PC1: держать `schema_version` равной 1, пока модуль не выпущен, а потом менять версии явно.

**Дальше.** PC1 начинается со шва, который загружает плейбук по умолчанию на закреплённой ревизии и проходит эталонные тесты; затем идут швы доставки и локальная передача работы, и три первых демо стартуют, как только они будут влиты.
