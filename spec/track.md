## Why

The board's structure — element types, statuses, the producer–reviewer loop, the roles — is Go code inside task-board. The operators decided on 2026-09-24 that extracting it into an external, project-level configuration handled by its own module is the first priority: it lets anyone describe their own process, it makes the board usable beyond software, and the next board can reuse the module instead of rewriting it. The current board stays in maintenance; new capabilities arrive as modules connected through thin seams.

## Demo playbooks

Each demo takes a deliberately rough input and runs it through its playbook under one orchestrator. Chains show one playbook's output becoming another's input.

1. `dev-cycle` — today's delivery process, cleaned up, with the delivery invariants. After PC1.
2. `bug-hunt` → `dev-cycle` — a proven finding is offered to the fixing process on the same board. After PC1.
3. `scrum` over `dev-cycle` — a cadence composed over delivery, sprints holding stories by link, estimate fields delegated by the slot binding. After PC1.
4. Cafe operations with bookkeeping — inventory → purchasing → accounting: humans, a tool, timers, recurrence, signed events, a hand-off whose result comes back. After PC3 and the waggle amendment.
5. Incident → post-mortem → fix in `dev-cycle`.
6. Patent — research → draft → refuter → filing.
7. Agency — lead → estimate → project (`dev-cycle`) → invoice.

## Dependencies

- **Curator:** release Skillfile schema 2 from its flag; `dependencies.skills` gains `directory` selection, so an orchestrator can depend on a tool provider in its own repository; activation `on-demand` and a skills launch channel, so a role skill reaches only the launches that run its role (spec §8.1, §8.3; curator-spec issue #91, curator issue #91). Runtime-mode dependencies narrowed to commands already exist (curator-spec core §4.4).
- **Agent selection** (`skill-project-management/.specs/drafts/agent-selection.md`): the spec amends its §3 (need vocabulary and spelling), §4 (model admission in the committed data policy), §7 (admission without an operator file) and §8 (temporary relaxation), and launch profiles LP D1 (today's ceilings move to `Playbook.json` as `policy.data.models`) and D9 (the case without an operator file); `Playbook.json` supersedes its committed project layer for role needs, admission, data policy and waivers.
- **waggle:** approver signatures, hand-off offers and scope leases, which exist; and **an amendment**, decided on 2026-09-24, that is written into the waggle specification now and implemented with milestone CM2 (spec §17.2): a class for board approvals and signed transitions, an event class with expiry and de-duplication, a service principal kind for event bridges, a `coord` type that returns a hand-off's result, signed by a host key of the receiving board rather than by an orchestrator, user verification available to board policy, and delegation: signed grants and delegated acts whose chain the board verifies (waggle A1 §19.8). PC3 and the cafe demo need it; the PC1 demos do not.
- **Scheduler:** `task-board tick` is called every minute by a user-level system timer — a launchd agent on macOS, a systemd user timer on Linux — installed by one task-board command; the main loop takes it over later (spec §6.9). PC3.
- **Lease store:** the board's own lease on one machine; waggle's lease store (NATS JetStream KV, milestone CM2) for a board shared across machines. Until CM2 a shared board runs tick on one machine only.
- **Session host:** marks hosted sessions so the kernel can tell agent sessions from people (spec §4.2).
- **Hosting provider:** hosted check sets read the provider's required checks on the exact head that lands (spec §6.12). PC3.
- **Operator files:** `~/.curator/models.toml`, `runtimes.toml`, `engines.toml` and `network.toml`, together (spec §2.3); `runtimes.toml` carries machine capacity, today's `spawn.max_parallel` and suite cap. The operator-file commands through the `curator` umbrella (`curator models`, `curator runtimes`, `curator inference engines`, `curator network`), each owned by the component that owns its file, and their `confirm` verb with the operating system's user authentication: until they ship, the resolver honours no widening entry of these files (spec §2.3). How the files and their confirmations are protected at the OS level is open (spec §17.3).
- **task-board:** the seam for PC1, the delivery seams over today's commands, the local hand-off, `rejected` in the goal ledger, `policy.wip` over elements, check sets over today's landing-gate suite run by the kernel's executor, per-run speed recording, and the legacy reading of today's config keys.

## Risks

- Reproducing today's permissive status model exactly: the kernel has no transition table and several gates depend on run context (spawned run, own element, manual move). PC1 may accept documented differences instead of identity; spec §14 lists them.
- Authority is only as strong as the actor signal and the default branch: until hosted sessions are marked and actions signed, refusals for agent runs are a guardrail; a project without git, or one whose landings are not reviewed, weakens the revision in force.
- Signatures show that a person acted only when they carry user verification; keys that cannot carry it (Secure Enclave keys today) protect the key but not presence. v3.1 requires user verification by default for approvals, relaxations and halts where a project turns signatures on, with `hardware-bound` as the minimum assurance, so such a project needs FIDO keys for those acts or lowers the requirement to `if-supported`.
- Role skills stay visible to every session until Curator ships on-demand activation; the description stopgap depends on the model obeying it.
- Delegation carries a person's authority to an orchestrator: its safety rests on the project's ceilings and `never` rules, the grant's conditions and budgets, and, before signatures, on the operating system's user authentication at the grant. A delegation without a budget or an expiry that is too long should be the exception.
- Widening entries of the operator's files are honoured only after confirmation, so metered billing and standing answers stay unavailable until the operator-file commands ship.
- Two sources of truth for roles during migration (`.roles`, `~/.roles`, installed skills): the PC2 lookup order must be explicit and logged.
- PC1 grows by the delivery seams and the local hand-off that the early demos need; keep each seam a thin adapter over today's commands.
- Schema churn before PC1: keep `schema_version` at 1 until the module ships, then version changes explicitly.
