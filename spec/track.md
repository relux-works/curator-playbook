Roadmap: `wiki/roadmap/ecosystem-roadmap.md`, process-configuration line (it replaces the earlier playbooks track PB0–PB4 of `skill-project-management/.specs/drafts/playbooks-track.md`). Two further items are pending for trust.md and the waggle amendment, not for the freeze: companion signatures for board acts (item 15), and profiles as package content (item 16).

## Why

The board's structure — element types, statuses, the producer–reviewer loop, the roles — is Go code inside task-board. The operators decided on 2026-09-24 that extracting it into an external, project-level configuration handled by its own module is the first priority: it lets anyone describe their own process, it makes the board usable beyond software, and the next board can reuse the module instead of rewriting it. The current board stays in maintenance; new capabilities arrive as modules connected through thin seams.

## Demo playbooks

Each demo takes a deliberately rough input and runs it through its playbook under one orchestrator. Chains show one playbook's output becoming another's input.

1. `dev-cycle` — today's delivery process, cleaned up, with the delivery invariants. After PC1.
2. `bug-hunt` → `dev-cycle` — a proven finding is offered to the fixing process on the same board. After PC1.
3. `scrum` over `dev-cycle` — a cadence composed over delivery, sprints holding stories by link, estimate fields delegated by the slot binding. After PC1.
4. Cafe operations with bookkeeping — inventory → purchasing → accounting: humans, a tool, timers, recurrence, signed events, a hand-off whose result comes back. After PC3 and the waggle amendment.
5. Incident → post-mortem → fix in `dev-cycle`.
6. Patent — research → draft → refuter → filing.
7. Agency — lead → estimate → project (`dev-cycle`) → invoice.

## Risks

- Reproducing today's permissive status model exactly: the kernel has no transition table and several gates depend on run context (spawned run, own element, manual move). PC1 may accept documented differences instead of identity; spec §14 lists them.
- Authority is only as strong as the actor signal and the confirmation: until hosted sessions are marked and confirmations signed, refusals for agent runs are a guardrail, and PC1's trust stub is documented as no boundary. Agents run as the operator's OS user, so the stores, keys and binaries they must not change need OS-level protection or a separate account for agents (trust.md §12, §14).
- Signatures show that a person acted only when they need presence: only presence-bound keys confirm, whatever the project sets (trust.md §4). For other board acts `user_verified: required` needs FIDO keys, or the companion app once the operator decides it counts (spec §17.3 item 15), or the project lowers the requirement.
- Role skills stay visible to every session until Curator ships on-demand activation; the description stopgap depends on the model obeying it.
- Delegation carries a person's authority to an orchestrator: its safety rests on the project's ceilings and `never` rules, the grant's conditions and budgets, the rule that only the grantor's own sessions act under it, and, before signatures, on the operating system's user authentication at the grant and the session host's marks. Budgets need one counter, so before CM2 a budgeted grant works only on a single-host board. A delegation without a budget or an expiry that is too long should be the exception.
- Widening entries of the operator's files are honoured only after confirmation, so metered billing and standing answers stay unavailable until the operator-file commands ship.
- Changes to the process that are not on the allowlist wait for a person's confirmation, so they stall until someone confirms them, from the phone or, before the app exists, on the machine or from the operator's workstation for a headless node. Batching lets one confirmation cover every pending change, and the allowlist lets production edits, limits, goals and preferences take effect on commit; the operator chooses between this proposal and making every change wait (spec §17.3 item 13).
- Two sources of truth for roles during migration (`.roles`, `~/.roles`, installed skills): the PC2 lookup order must be explicit and logged.
- PC1 grows by the delivery seams and the local hand-off that the early demos need; keep each seam a thin adapter over today's commands.
- Schema churn before PC1: keep `schema_version` at 1 until the module ships, then version changes explicitly.

PC1 starts with the seam that loads the default playbook from the head of the default branch, with legacy mode, and passes the goldens; the delivery seams and the local hand-off follow, and the three first demos start as soon as those land.
