The three most important findings:

1. **F1: any agent can act as a human owner, an approver or an event source.** The spec accepts "a board action" as a human approval and never says who may fire a transition or emit an event. Today the only actor signal is the `TASK_BOARD_RUN_ID` convention. That contradicts waggle's mandatory "authority outside the model" layer. An agent can approve its own spending, waive its own independent review, or post `tool.passed` for the Lean check.
2. **F2: package bytes choose what runs.** `tool` owners are free-form command or webhook strings in a package's `data/playbook.json`, and the kernel invokes them on entry. `notify`, `schedules` and `spawn.owner` let a package trigger side effects. Needs such as `effort: max` come from the package. No project-level admission of playbooks remains. This reopens the package-influence boundary that Curator (environments §10.3, core §3) and the superseded playbooks draft (§12) closed.
3. **F3: the PC1 target fails the spec's own validator.** `default.playbook.json` would be rejected by the rules the spec requires task-board to run at load: the capability check (`review.accepted` on `* → integrating`, whose sources are owned by non-reviewers), an unprovided guard (`integration.external-evidence`), and events that no module provides. As written, task-board cannot load its own default. Close behind, F4 and F5: several §14 claims about today's code are false, for example that containers never leave `done`/`closed`, and that `integrating` is left only by integration.

## 2. Findings

### Blocking

#### F1. Human owners, approvals and events can be exercised by any agent
- **Type:** authority · **Severity:** blocking · **Decision:** H1
- **Claim:**
  - spec:228: "For human approvers the approval is a board action or a waggle approver signature (`waggle/spec/waggle.md`), recorded with the element."
  - spec:378: `ask` is "request the operator's approval — a board card or a waggle approver signature".
  - spec:104: `human` owners are "resolved by the operator or project directory".
  - spec:210: events arrive when "a tool reports, a webhook fires".
- **Conflicts with:**
  - `waggle/spec/waggle.md:237`: "| 1. Authority outside the model | gates, scope leases, supervisor-executed `cancel`/`halt`, signature policy | yes |" (the Mandatory column).
  - waggle.md:387: "in production authority stays outside the model: leases, gates and the signature policy decide".
  - waggle.md:23: "`TASK_BOARD_RUN_ID` is a convention".
  - `tools/board-cli/cmd/producer_handoff_guard.go:12-15`: "This is a spawned-role workflow guardrail, not an operator authorization boundary: untracked operators retain ordinary set_status administration."
- **Derivation:**
  - The kernel's only actor signal is the `TASK_BOARD_RUN_ID` environment variable (`producer_handoff_guard.go:33-36`). A primary-session orchestrator agent is indistinguishable from the human operator.
  - With "a board action" accepted as approval, the orchestrator can do the following. Each defeats the example that was written to show it:
    - approve cafe spending (`cafe.playbook.json:57`, `:76`);
    - approve its own "same-publisher review for this epic, 30 days" (spec:381);
    - leave any `human`-owned state (`escalated`, `decision-needed`, `blocked`, `stalled`).
  - The spec never says who may fire a transition out of a state: its owner, or anyone. It never says who may emit an event either. So `tool.passed` (`prove2me-style.playbook.json:73`) or `payment.received` (`cafe.playbook.json:87`) can be posted by the agent under test.
  - waggle has no approval message for board gates. Its classes are `coord`, `cmd`, `report` and `receipt`, and approvals are co-signatures on those (waggle.md:212-225, :160-183). `who` names have no mapping to roster principals (spec §17 open question 5).
- **Resolution:**
  - Define an actor model. Every transition records its actor class: a spawned run with its role, a primary session, a human signature, a kernel-invoked tool with its exit status, or an authenticated external event.
  - Human-owned transitions, `approvals` and `ask` require a waggle signature from a roster principal that the operator or project directory maps from `who`. Drop "board action", or restrict it to a channel the kernel can authenticate.
  - Tool events come only from the kernel's own invocation. Webhook events need signed payloads.
  - State which actors may fire transitions out of each owner kind.
  - Specify a waggle message type for board approvals.

#### F2. Package bytes select executed programs, side effects and launch parameters, with no project admission
- **Type:** authority · **Severity:** blocking · **Decision:** H2 (and H3 for effort)
- **Claim:**
  - spec:105: a `tool` owner is "a program, module hook or webhook", named by the free-form `tool` string (schema:299-302).
  - spec:221: tool owners get "tool invocation on entry".
  - Examples: `"tool": "task-board worktree integrate"` (`default.playbook.json:32`), `"lean-kernel-check"` (`prove2me-style.playbook.json:11`), `"webhook:supplier-portal"` (`cafe.playbook.json:12`), `notify` (`cafe.playbook.json:76`), `schedules` (spec §6.6), and automatic `spawn.owner` actions (spec:197).
  - Templates ship as package data: spec:325 has `data/playbook.json` and spec:328 has "data/role.json — capability, default needs". Needs carry `effort: max` (`dev-cycle.playbook.json:12`).
  - spec:354: templates are resolved "by finding the installed skill whose `data/playbook.json` has that name".
- **Conflicts with:**
  - `curator-spec/protocol/environments.md:94-98`: "Profiles are data end to end. … No adapter, materializer, form, mode, or channel is ever selected by package bytes".
  - environments.md:3143-3146: "A profile chooses what the context says, never how a process is launched. This is the package-influence boundary of the core execution policies".
  - `core.md:85-91`: a manager "MUST NOT transfer execution control to a package- or repository-selected program, argument vector, environment, hook".
  - PB §12 (`.specs/drafts/playbooks.md:218-219`): "A playbook grants no authority … A playbook never selects models, efforts, runtimes, permissions, network or sandbox profiles (AS)."
  - AS §4 (`agent-selection.md:67`): the project admits playbooks with `"playbooks": { "allowed": ["dev-cycle@^1", "bug-hunt@^1"], … }`. The spec has no equivalent.
- **Derivation:**
  - A playbook is installed by Curator as skill data. The board then executes the programs that data names, runs its schedules and spawns its roles.
  - A third-party `curator-playbook-*` package, or any installed skill that claims a template name (see F20), can therefore run arbitrary commands on state entry. It can also send element fields (amounts included) to a webhook through `notify`.
  - Formally, Curator's rule binds Curator's own components. The ecosystem's boundary is still bypassed one layer up: bytes that Curator carefully keeps inert become executable in task-board.
- **Resolution:**
  - A playbook names tools; it never spells them. The binding from a tool name to an executable or URL, with an allowlist, lives in operator or project configuration, like `runtimes.toml`.
  - `spawn.owner`, `notify`, `handoff` and schedules run only for playbooks the project admits.
  - Restore a project admission list (AS §4) or define its replacement.
  - Effort in needs: see F9.

#### F3. The PC1 target playbook fails the validator task-board must run at load
- **Type:** internal · **Severity:** blocking
- **Claim:**
  - spec:385: "task-board runs it when it loads a playbook".
  - spec:112: "A guard that requires a capability refuses an owner without it".
  - spec:393: "guard review.accepted needs a reviewer, owner developer is a producer".
  - spec:224: "The validator refuses a guard or action no loaded module provides".
  - spec:18: the default is what "PC1 makes the kernel read".
- **Conflicts with** `examples/default.playbook.json`:
  - Lines 117-123: `* → integrating` guarded by `review.accepted`. `*` expands to `backlog`, `analysis`, `to-dev`, `development`, `to-review`, `reviewing` and `blocked` (spec:207). Six of them are owned by non-reviewers (orchestrator, analysts, producer/tester, approver), so the capability rule fires six times.
  - Line 139: guard `integration.external-evidence` is in no provider row of spec:217-222.
  - Line 151: event `blockers.terminal` is in no provider row either. Only `tool.passed` and `tool.failed` are listed as events.
  - The same gap hits every other example: `delivery.validation-passed`/`-failed`, `delivery.integrated`/`-integration-failed`, `handoff.terminal`, `supplier.confirmed`/`shipped`, `payment.received`, `child.accepted`.
- **Derivation:** under the spec's rules, loading the default fails. Two escape routes exist: events are exempt from the provider check, which leaves typos in event names to create dead transitions silently; or capability checks skip `*` sources. The text states neither. The §10 prototype claim (spec:402) is accurate only because capability and provider checks were not run.
- **Resolution:**
  - Define, per guard, which role the capability requirement applies to: the actor that produced the verdict, or the owner of the source state. Define how it applies to `*` sources.
  - Publish a complete provider table per module: guards, actions, events and `via` commands.
  - Run the full check set on `default.playbook.json` before PC1.

#### F4. Containers do leave `done` and `closed` today, and `derived_status` is undefined against `terminal` and `locked`
- **Type:** decision-conflict (code) · **Severity:** major
- **Claim:**
  - spec:458: "done and closed are terminal and never exited | `pkg/board/escalation.go:105-107`, `pkg/board/terminal_status.go:16-21` | `terminal`, no `reopen`".
  - spec:184: "without one, terminal is final (today's rule, §14)".
  - The container workflow marks `done` and `closed` terminal (`default.playbook.json:167-168`) and marks `integrating` `locked`, with the single exit `via: integrate` (`:166`, `:178-184`).
- **Conflicts with:**
  - `pkg/board/escalation.go:151-162`, the comment: "Only a real active aggregate may reopen a closed container".
  - escalation.go:198-200: `if old == StatusDone || old == StatusClosed { action = Reopened }`. Aggregation writes the new status without `RefuseTerminalTransition`; that check is applied only to the directly mutated element (`consistency.go:163`).
  - escalation.go:65-68: "A container reads `integrating` exactly when a child is `integrating`". Containers therefore enter and leave `integrating` by aggregation, not by `accept_cr` or `integrate`.
  - Direct container statuses other than `closed` are admitted today: only the close is gated (`validation.go:34`), and blocked containers are preserved (`escalation.go:151`; `cmd/validate.go:496`).
- **Derivation:**
  - The probe finds that all eight container states other than `backlog` and `closed` are unreachable by declared transitions.
  - If aggregation obeys `terminal` and `locked`, the default loses three behaviours: container reopen, integrating rollback propagation, and manual blocking.
  - If aggregation bypasses them, the §6.1 rules and the "terminal exits" check (spec:400) do not hold for `derived_status` types.
- **Resolution:** define `derived_status` precisely. Say which declared rules aggregated moves obey. Declare container reopen explicitly (derived transitions with `reopen: true`). Correct the §14 row, and list manual container statuses as mapped or as a documented difference.

#### F6. The `via` rule contradicts the default's own routes, and `*` precedence is undefined
- **Type:** internal · **Severity:** major
- **Claim:** spec:208: "`via` names the one command that performs the transition …; any other route to that state is refused."
- **Conflicts with:**
  - The default has three routes into `done`: `via: integrate` (`default:131-137`), `via: integrate_external` (`:139`) and the inline `* → done` (`:140-145`). Read literally, each `via` refuses the other two.
  - Read narrowly (per `from → to`), `reviewing → to-dev via reject_cr` (`:124-130`) overlaps `* → to-dev` (`:103`), whose expansion includes `reviewing`.
  - Merge keys are `from → to (+via)` (spec:294), so a `*` rule and an explicit rule on the same pair coexist with no precedence.
- **Resolution:** make `via` a property of one `from → to` pair, not of the target state. Define that an explicit transition shadows the `*` expansion for the same pair, or that the validator refuses the overlap.

#### F7. `one_of` owners contradict "exactly one owner per state" and yield zero owners at runtime
- **Type:** decision-conflict · **Severity:** major · **Decision:** H5
- **Claim:** spec:182: "the owner is `{ "one_of": [...], "by": "assignment.role" }`: still exactly one owner per element. *proposed*". Used in `default:78, 83`.
- **Conflicts with:**
  - `wiki/decisions.md:17`: "every state has exactly one owner and optional helpers". The rule is per state, not per element.
  - There is no structured `assignment.role`. Spawn writes the display string `[archetype] role (agent)` (`cmd/spawn.go:3856`; `role.go:247-249`). Manual assignment is free text: `assign(ID, agent=<name>)` (`validation.go:87`). Every spawn overwrites the assignee, reviewers included.
- **Derivation:**
  - A manual move to `development` after `reject_cr` carries a stale `reviewer` assignee (or `ivan`). The owner is not in the set, so the element has zero owners, which breaks spec:180.
  - The validator cannot check capabilities of a `one_of` statically.
  - `spawn.owner` needs the owner in order to spawn, while the owner is defined by the assignment the spawn writes: a circular definition.
- **Resolution:** either keep one owner per state (split `development` per role, or model the variant role as a field that must be set on entry), or amend the decision explicitly with a structured `assignment.role` field set before entry and a rule for when it is absent.

#### F12. `degrade` mutates the workflow at runtime and cannot restore independence
- **Type:** impossible · **Severity:** major
- **Claim:** spec:379: "`degrade` | run on the best available, mark the result degraded and insert an extra review state before the next terminal state". Used for the independence requirement at `bug-hunt:23`.
- **Conflicts with:**
  - spec:16: the validator "checks a configuration before anything runs".
  - spec:47: the semantic digest is taken over the resolved playbook.
  - The inserted state's owner and capability are undefined.
- **Derivation:** the unmet need is `not_same_publisher_as: hunter`, and it is unmet precisely because only one publisher is available. The extra review then runs on that same publisher. Independence cannot be restored by adding reviews from the same source.
- **Resolution:** declare the degraded path statically (a named `degraded-review` state and its owner, validated like the others). Forbid `degrade` for independence requirements, or require a human owner for the inserted review.
