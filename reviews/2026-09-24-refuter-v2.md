## 2. Findings

### Blocking

#### R1. `policy.wip` limits runs, not elements, and moves a machine limit into the committed file

- **Type:** decision-conflict · **Severity:** blocking
- **Claim:**
  - spec:394: "`policy.wip` bounds active runs, the runs working the board's elements".
  - spec:400: "`board` bounds the active runs of the whole board; `per_role` those of one role; `per_state` those working elements in one state".
  - spec:401: "When starting a run would exceed a limit, the kernel does not start it: the element keeps its state, the start waits".
  - spec:54 and :403: "the per-board run limit `spawn.max_parallel`, which becomes `policy.wip.board`"; spec:819 maps "child runners per control root, `spawn.max_parallel`" to `policy.wip.board`.
  - spec:889 (§17.2 row 17) and wiki `decisions:124`: "`policy.wip` bounds active runs per board, role and state", recorded as the operator's decision.
- **Conflicts with:**
  - ops:121, item 17: "take it now as `policy.wip`: the maximum of elements per state, per role and per board; over the limit the board does not start a run" ("максимум элементов на шаг, на роль и на доску; сверх лимита борда run не запускает"). Accepted at ops:143.
  - ops:144, the correction to 15: "machine limits (parallel runs, check runs) go not into the committed `task-board.config.json` but into `~/.curator/runtimes.toml`; `policy.wip` in `Playbook.json` describes the process" ("лимиты машины (параллельные run'ы, прогоны проверок) … в `~/.curator/runtimes.toml`; `policy.wip` в `Playbook.json` описывает процесс").
  - tbc:189: `spawn.max_parallel` is a "Per-client concurrent runner limit", default 20 (spawn.go:13-15). tbc:212-213: it "bounds child runners per control root". runtime.go:3408-3431 counts running records from `listSpawnRunStates(manifest.WorkDir)`, stored under `<workDir>/.temp/spawn-runs` (runtime.go:4481-4482), "the gitignored .temp/spawn-runs/ tree" (runtime.go:369).
  - spec:789: the default reproduces "every row … unless it says otherwise".
- **Derivation:**
  - **Unit.** Elements and runs diverge wherever an element sits in a state without a run: queued for a reviewer, `accepted` waiting for integration, or a human-, tool- or process-owned state. Under v3, `per_state: {"dev.development": 3}` admits any number of elements in development as long as three runs are active, because "the element keeps its state, the start waits". A limit on a human-owned state, such as "no more than five orders awaiting approval", cannot be expressed: no run works that state.
  - **Placement.** The operator named parallel runs as a machine limit for `runtimes.toml`. v3 turns the one parallel-run key task-board has into a committed process key. The spec contradicts itself on the key's scope: §14:819 says "per control root", while §2.1:54 and §6.8:403 say "per-board".
  - **Observability.** Run records live in each checkout's gitignored `.temp/spawn-runs`. On a board shared by teammates, "the active runs of the whole board" is therefore unobservable until a shared store exists (CM2), and the spec says nothing about it. Element counts are observable, because board elements are committed and published.
  - **PC1 target.** `default.playbook.json` sets no `policy.wip` (default:199-205), and neither §6.8 nor the schema gives a default. Today's cap of 20 runners per control root is not reproduced, and §14 does not list the difference.
  - **Record.** Spec §17.2 row 17, §20 row 17 and wiki `decisions:124` would freeze the author's reading as the operator's decision.
- **Resolution:**
  - Count elements, as the operator worded it. `per_state` counts elements in the state. `per_role` counts elements whose current state is owned by the role, or whose `assignment.role` is the role. `board` counts elements in states the spec names as in progress, for example non-initial non-terminal states. Over a limit, the kernel does not start the run that would take in another element, and it reports `wip_limit_reached`.
  - Map `spawn.max_parallel` onto machine capacity in `runtimes.toml`, not onto `policy.wip.board`. Give the default playbook today's behaviour, or state the kernel default.
  - Correct spec §2.1, §6.8, §14, §17.2 row 17, §20 row 17 and wiki `decisions:124`. If run-based limits are wanted, that is a new operator decision (§4).

### Major

#### R2. Check-set evidence is produced in the environment of the actor it gates

- **Type:** authority · **Severity:** major
- **Claim:**
  - spec:463: "`commands` are run in order by the kernel on this machine".
  - spec:466: "The delivery module produces it, as today's suite does: it runs a local set when a producer hands off and again at integration … The guard only checks that the evidence exists."
  - spec:467: only the local mirror uses "a clean checkout of the exact head".
- **Conflicts with:**
  - spec:437 and :439 (tools): "A tool's verdict must not come from the actor that triggered it … The actor of the entering transition never runs it." spec:442: "The environment is sanitized: a fixed `PATH` … and no variables inherited from agent runs."
  - ops:12 (decision 1, accepted): the board runs the tool itself in a clean environment, not the agent that brought the work to it, "otherwise the agent slips in its own `lean` and 'proves' anything".
  - Today's suite: tbc:416-417, "The producer runs it at Change Request build". validation.go:430-431 runs `exec.Command("/bin/sh", "-c", trimmed)` with `cmd.Dir` set and no `cmd.Env`, so the suite inherits the environment of the process that invoked it.
- **Derivation:**
  - `delivery.checks-passed` gates dev-cycle's review and its inline done (dev-cycle:176, :189). The `landing` set gates integration.
  - Produced "as today's suite does", the `handoff` set runs inside the producer's own `task-board` call, with the producer's `PATH`, its variables and its worktree. A `make`, `go` or `test` shim earlier on `PATH` records passing evidence that no reviewer sees in the diff.
  - The spec demands a clean checkout only for the mirror, the rarer case. This is refuter v1 N7's class: v2.1 closed it for tools, and v3 reopens it for the evidence that gates every delivery transition.
- **Resolution:** run local sets through the kernel executor of §6.11 or its equivalent, never in the process of the actor whose transition they gate. That means a clean checkout of the exact tree and a sanitized environment, with the executor recorded next to the evidence.

#### R3. Mirror evidence both satisfies and does not satisfy a hosted set

- **Type:** internal · **Severity:** major
- **Claim:**
  - spec:466: "The guard only checks that the evidence exists."
  - spec:467: "When hosted checks cannot run for a verified external cause, the local-mirror rule applies: a clean checkout of the exact head runs the matching commands and records the evidence. The mirror never produces, edits or stands in for the provider's own status, so branch protection still waits for the provider."
  - spec:462: "every place listed must pass".
- **Conflicts with:**
  - The operator's delivery policy that the rule comes from (`~/.agents/.instructions/INSTRUCTIONS_WORKFLOW.md`, "External-CI local mirror fallback", source repo relux-agents-infra): "Local evidence supplements the unavailable hosted execution; it does not satisfy a required hosted status". The spec neither cites nor defines "the local-mirror rule".
- **Derivation:**
  - If the mirror's record is "the evidence" of the hosted half, the guard passes and dev-cycle's `delivery.integrate` goes on to land while the provider's required checks never ran. On a repository without branch protection, which the spec never requires, the head lands with no hosted run at all.
  - If it is not, the mirror changes nothing on the board, "records the evidence" misleads, and the gate waits through an outage with no declared exit.
- **Resolution:**
  - Record mirror evidence as `mirror`, never as the hosted half of a set.
  - State what the board does while hosted checks are unavailable: wait, or accept an explicitly signed human override.
  - Cite or define the rule.

#### R4. The landing gate can be left out, and the default names no set

- **Type:** decision-conflict (code) · **Severity:** major
- **Claim:**
  - spec:337: "`delivery.integrate` integrates the accepted revisions of the unit, gated by the check set its `checks` argument names".
  - spec:451: the gate is named "as the gate of an integration, `{ "action": "delivery.integrate", "checks": "landing" }`".
  - spec:469: "A set a playbook names must be defined in `task-board.config.json` … the validator checks it portably".
  - spec:834 (§14.11): "The default keeps today's guard `delivery.integration-evidence` on its `integrate` route; that evidence is the result of the `landing` check set".
  - The schema types `checks` but does not require it (schema:2094-2111); probe: `{"action": "delivery.integrate"}` validates.
  - spec:320: "`actions` run after the move".
- **Conflicts with:**
  - tbc:425-427: "An **absent** `validation` block … refuses `worktree integrate` with `validation_not_configured` before any ref moves. The gate defaults to refusing, not to passing." spec:818 repeats: "an absent block refuses integration".
  - spec:426: "A playbook may add stricter checks, never weaker ones".
- **Derivation:**
  - A project that extends dev-cycle may replace `in-progress → integrating` (merge rule 3, spec:501; actions are replaced whole, spec:502) with a bare `delivery.integrate`. No set is named, so none gates the integration. No §6.10 invariant and no §10 check covers the case, and the project's stories land with no suite, which today's kernel refuses by default. This is refuter v1 N19's class, a delivery gate escaped by omission: closed for the four invariants, open for the landing gate.
  - The default names no set, so the portable check at spec:469 never asks for `checks.landing`. `delivery.integration-evidence` is tied to a set name that no playbook contains. The spec does not say what a default-based project without `checks.landing` or the legacy key does; today it refuses.
  - The failure path is also unstated. The action runs after the story entered the locked `integrating`, whose exits are only `delivery.integrated` and `delivery.integration-failed` (dev-cycle:137-143). Nothing says that a failed set emits the latter with a rollback authorization.
- **Resolution:**
  - Make the landing gate part of the delivery module: `delivery.integrate` requires `checks`, or defaults to `landing`, and an undefined set refuses integration as today.
  - Have the default name `landing` explicitly, for example as an argument of `delivery.integration-evidence`.
  - State that a failed or unavailable set emits `delivery.integration-failed` with its authorization.

#### R5. Check-set evidence is undefined for inline work, yet dev-cycle requires it there

- **Type:** impossible · **Severity:** major
- **Claim:**
  - dev-cycle:176 and :189: `{ "guard": "delivery.checks-passed", "set": "handoff" }` on `development → review` and on the inline `development → done`. Inline work has no Change Request: `delivery.review-ready` "passes for an element without a Change Request" (spec:337), and `delivery.cr-absent` guards the done route.
  - spec:337: the guard "passes when the named check set has evidence for the revision the transition moves".
  - spec:466: "a local set to the tree it ran on … when a producer hands off".
  - dev-cycle:54: "metadata and research work is usually inline". scrum-config:11 gives only `docs` an empty variant.
- **Conflicts with:** tbc:448-450: "The rest of the isolated workflow — provisioning, Change Requests, review, rework, `worktree checkpoint` — does not read this key; only integration and producer-side evidence recording do." Today inline work runs no suite.
- **Derivation:**
  - An inline dev-task has no revision and no Change Request tree for "the transition moves". For the `metadata` and `research` classes the example runs `make test-fast`, but the spec does not say on which tree (the shared checkout's working tree, which other sessions also change? `HEAD`?), who runs the set without a Change Request build, or what the evidence binds to.

#### R6. Change Request work whose review level is `none` has no route out of development

- **Type:** internal · **Severity:** major
- **Claim:**
  - dev-cycle:60: "none lets inline work finish on the producer's outcome; work under a Change Request always needs a reviewer's acceptance (invariants 2 and 3)".
  - dev-cycle:177: `development → review` requires `{ "guard": "field", "name": "review", "in": ["required", "light"] }`.
  - dev-cycle:186-190: `development → done` requires `review` `is` `none` and `delivery.cr-absent`. dev-cycle:193: "Work under a Change Request cannot take this route … so it still needs a reviewer's acceptance."
  - dev-cycle:203: `accepted` is entered only from `review`, via `accept_cr`.
  - spec:830 (§14.7): the goal ledger "accepts a `none` item on the producer's outcome alone", a kernel effect "keyed on the same field".
- **Conflicts with:**
  - ops:96 (13a): "with `none` the element goes past review" ("при `none` элемент идёт мимо ревью").
  - The description's own promise that such work still reaches a reviewer.
- **Derivation:**
  - A dev-task under a Change Request with `review: none` cannot enter `review` (field guard) nor `done` (`cr-absent`), and `accepted` is reachable only from `review`. That review level is a legal value, and it is every new element's value when a project sets `policy.review.default: none`.
  - The element can leave development only to `blocked` or `closed`. Its story's join on accepted, approved, done and closed never passes until someone edits the field.
  - Meanwhile the goal ledger, kernel code shared by every board, accepts the item on the producer's outcome (goal_acceptance.go:167-170). The ledger calls it accepted while the workflow cannot deliver it.
  - Today such an item is ledger-accepted while its Change Request still integrates through `accept_cr`. v3's routes give it no way to reach `accept_cr`.
  - §14.7 presents the ledger effect as part of the default's mapping, but it applies to dev-cycle too. The review level thus remains a kernel meaning outside the playbook: the option 13b that the operator rejected.
- **Resolution:**
  - Drop the field guard from `development → review`, so that any level may be reviewed and `none` may also finish inline. Or add a route into review for Change Request work under its own `via`.
  - State how the ledger's `none` acceptance relates to playbooks that route `none`, for example that it applies only where the playbook declares no `field` route on `review`.

#### R7. Field-routed decisions and approvals do not bind the values they depend on

- **Type:** authority · **Severity:** major
- **Claim:**
  - spec:339: "A threshold selects whether a purchase needs an approval: `{ "guard": "field", "name": "amount", "gt": 500 }` beside the `approvals` guard".
  - spec:732: "an entry without the guard is admitted when its `field` condition admits no value that the `field` condition of any guarded entry admits … so `amount lte 500` may skip the approval that `amount gt 500` requires". spec:736: the prototype admits exactly that.
  - spec:443: the tool receives "the element's id, type and declared fields", read when tick runs it, every minute (spec:409).
  - spec:343: evidence is fresh when "recorded after the element last entered the transition's source state"; under a Change Request it must also name the revision. Nothing is said about field values.
  - The spec has no rule on who may write an element's fields; the only write rule concerns lease crossing (spec:524).
- **Conflicts with:**
  - waggle:463-471 (A1 §19.1): the payload binds "the element fields shown to the approver … An approval therefore cannot be replayed … for another amount."
  - waggle:596-604 (A1 §19.7): the board decides "freshness: an approval counts only for the state entry it names and, under a Change Request, for the revision it names". There is no field check on either side.
  - Today any actor may change `review` through `set_details` (mutations.go:520-548; activity_mutations.go:39).
- **Derivation:**
  1. **Threshold.** Take the cafe with the threshold routes that §10's prototype admits: an unguarded `draft → sending` for `amount lte 500`, beside approvals guarded by `amount gt 500`. A buyer run creates an order for 450 and fires `draft → sending`. Tick runs the tool up to a minute later and reads the fields then. In between, the run sets `amount` to 4500 and adds lines. The supplier receives an unapproved order of 4500 through a route the validator certified.
  2. **Approval.** A manager approves 620, and A1 binds "shown" 620. The amount changes to 6200 while the order waits in `approval`. The approval is still fresh under §6.3, and the board checks only entry and revision, so `approval → sending` sends 6200. A1's "cannot be replayed … for another amount" is enforced by nobody. Unsigned approvals, the default without a signature policy, bind no field at all.
  3. **Review level.** A developer run sets its own dev-task's `review` to `none` and takes `development → done` inline, skipping review. In v2.1 every dev-task went through review; the field route makes the field authority-bearing.
  4. Whether the exception also exempts a `risk` marker is unstated: spec:732 speaks of "the guard". If it does not, a small order from the agent-owned `draft` must carry `risk: spending`, and in the cafe project a signed human act. If it does, the project's `spending` signature does not cover small orders.
- **Resolution:**
  - Treat fields read by a guard as authority-bearing. Freeze them from the guarded transition until the element leaves the target state, or hand the tool the values recorded at entry, keyed by (element, entry).
  - Bind every approval, signed or not, to the fields it depends on, and refuse one whose shown values differ from the current ones. This is the board side of A1 §19.1; update §6.3, §6.4 and A1 §19.7 together.
  - State who may write fields. At least: a run may not write a field that a guard on its own element's exits reads, and `review` is set by the orchestrator or a person.
  - State whether the exception covers `risk`.
