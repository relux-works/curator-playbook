## 2. Findings

### Blocking

#### V1. Item 4's path check does not see triggers, limit redirects, state keys or owners, so production edits move work past a tool, a reviewer, a signed event and a role's requirements on commit

- **Type:** authority · **Severity:** blocking for item 13's proposal as the draft applies it. The alternative in §17.3 item 13 is unaffected.
- **Claim:**
  - spec:40: "A proposed version takes effect on commit only when every difference from the version in force is on a small allowlist that cannot move authority".
  - spec:1203: "while everything that can move work past a person, a tool, a guard or a verification state still waits".
  - spec:204 defines the edits: "adding, removing or re-owning production states and the manual transitions between them … each such transition carries only hygiene guards (…) and the actions `spawn.owner`, `assign` and `notify`".
  - spec:204 defines the gates: "A gate is a state that is not a production state, a guard that is not a hygiene guard, a state's `requires`, a `risk` marker, a `limit`, or an action other than the three above."
- **Conflicts with:**
  - ops:177: "Полномочные разделы `Playbook.json` вступают в силу после аутентификации человека"; row 26 (spec:1177).
  - spec:885: a hard requirement is relaxed for the whole team "only [by] a change to the project's `Playbook.json`, which, being in the authority projection, takes effect once it is committed and a person has confirmed it".
  - spec:945: automatic entries triggered by "a declared signed external event carry their own authority — … a signer group the project bound".
  - spec:456: "Only the kernel writes a field that `record_source` names: no run, session or person does, so no actor can steer where the element resumes."
- **Derivation.** Each probe below is valid against the schema and passes the literal model (§1).
  - **(a) Triggers are not gates.**
    - cafe:87 and cafe:89: `awaiting-confirmation` and `confirmed` are owned by `cafe-orchestrator`, so both are production states. The only direct edge between them is automatic, on `supplier.confirmed` (cafe:112).
    - A commit adds `{ "from": "awaiting-confirmation", "to": "confirmed" }`. Its key differs from the automatic edge's by `on` (spec:479: "so may a manual move and an automatic one between the same two states").
    - The in-force edge has no gates, so the new edge is not weaker. The guard-bypass rule finds no `approvals` guard or `risk` marker on any entry into `confirmed` (spec:945).
    - The orchestrator now marks orders confirmed without the supplier bridge's signed event, and the fifteen-minute escalation to the manager (cafe:113) never fires.
  - **(b) `limit.then` is an edge the check does not model, and a `limit` counts as a gate.**
    - In formal missions, `proving` (owner `prover`) is a production state. `accepted` is reached only through `checking`, the Lean tool (prove2me:79-86).
    - A commit adds a production state `drafting` (owner `prover`), a transition `proving → drafting` with `"limit": { "max": 1, "then": "accepted" }`, and `drafting → proving`. The check sees a cycle among production states with one more gate.
    - At run time the prover's own run fires `proving → drafting` twice. The second firing lands in `accepted` (spec:482), which needs no resolution. Milestone `open → proven` then fires on `children.changed` (prove2me:66-71). A lemma is proven without the Lean kernel.
    - In dev-cycle an inline task reaches `done` the same way. Invariant 1 (spec:596) stops only work under a Change Request.
  - **(c) A new production state may carry any state key.**
    - In dev-cycle, `review` (enum `required`, `light`, `none`) is read by the `field` guard of `development → done` (dev-cycle:56-60, :188-199).
    - A commit adds production states `none` (owner `developer`) and `park` (owner `orchestrator`, `"record_source": "review"`), with `development → none → park → development`. The validator admits it, because `review`'s type admits the source state `none` (spec:456).
    - On entry into `park` the kernel writes `review = none`. Inline work then finishes through `development → done` with no reviewer.
    - From then on only the kernel writes `review`, so neither the orchestrator nor a person can set it back (spec:415, :456).
    - Likewise, an element moved into a new production state with `locked: true` escapes every `from: "*"` transition (spec:455, :478), an automatic `*` escalation included.
  - **(d) The owner of a production state carries authority that no gate represents.** The owner decides several things for the work in its state:
    - whose hard needs apply, and whose `on_unmet`;
    - whose effort floor applies (spec:553);
    - whose per-role model admission applies (spec:867);
    - in a composition, which orchestrator's lease covers the work (spec:695).

    Re-owning is on the allowlist, and the author's prototype lets it through (spec:987).
    - **Independence.** In dev-cycle, re-owning `development` to `designer` (dev-cycle:32) leaves the reviewer's `not_same_publisher_as: developer` (dev-cycle:19) pointing at a role that no longer produces the evidence. spec:837 evaluates it against "the run of that role that recorded the outcome", and no such run exists, so independence is silently dropped or unmet. The author's own probe that drops independence through a role contribution waits (spec:997).
    - **Hard needs.** Suppose a production role requires `local: true` or carries a per-role model restriction. Re-owning its state to another production role sends the work to any admitted model. That is a permanent relaxation for the whole team made without a person, against spec:885.
- **Resolution:**
  - **Count triggers as gates.** An automatic edge carries its trigger as a gate: the event name, `after`, and the signer group of a declared event. A manual twin is then weaker and waits.
  - **Narrow production transitions.** One carries only `from`, `to`, hygiene guards, the three actions, `description` and `ui`: no `limit`, `via`, `risk`, `reopen` or `resolution`. Model every `limit.then` of every transition as an edge that carries that transition's guards.
  - **Narrow production states.** A new or re-owned production state carries only `owner`, `description` and `ui`, with helpers under item 3. Any of `requires`, `record_source`, `clear_on_exit`, `locked` or `resolution` on a new or changed state takes the edit off the allowlist. Separately, the validator should refuse a `record_source` field that any guard reads outside the exits of that state.
  - **Treat the owner as a gate.** The gate carries the role's hard needs, `on_unmet`, effort floor, per-role model admission and orchestrator lease. Re-owning or adding a state is allowlisted only when these are at least as strict. Define independence against the run that produced the evidence, whatever its role (spec:837).
  - **Occupied states.** Say that removing a production state that elements occupy needs `migrations` (spec:676). They move elements without a transition, and they are not on the allowlist.
  - **Prototype.** Re-run the classification prototype on these four probes and on V2's.
  - **Or,** for the PC1 freeze, take item 13's alternative (§5, D1).

#### V2. Item 3 is not authority-neutral: work-in-progress limits on a person's states suppress escalations

- **Type:** authority · **Severity:** major
- **Claim:**
  - spec:203 allowlists "estimate dimensions and scales, helpers, `policy.goals`, `policy.capacity` and `policy.wip`".
  - spec:1203: "everything that can move work past a person … still waits".
- **Conflicts with:**
  - spec:570: "A manual or agent transition that would take an element over a limit is refused with `wip_limit_reached`".
  - spec:568: `per_role` "counts the elements whose current state the role owns".
  - dev-cycle's escalation routes:
    - `challenge → decision-needed` on `human-decision-needed` (dev-cycle:114);
    - `review → escalated` on `stop_the_line` (dev-cycle:207);
    - the fourth rework, redirected to `escalated` (dev-cycle:200-206).
  - spec:1033: "`human-decision-needed` → `decision-needed`, owned by a person".
- **Derivation:**
  1. In the scrum project, a PC1 demo, an agent commits `"per_role": { "dev-cycle.operator": 1 }`. This is item 3, so it takes effect on commit. The schema's minimum of 1 does not help, because one parked element fills the limit.
  2. The orchestrator moves one blocked task to `escalated`. That is a manual exit of an orchestrator-owned state (dev-cycle:241).
  3. From then on every entry into an operator-owned state is refused.
     - A refuter's `human-decision-needed` leaves its epic in `challenge`. A second refuter run's `no-contradiction` is fresh, because the epic never left `challenge` (spec:505), so it moves the epic to `in-progress` (dev-cycle:115).
     - A reviewer's `stop_the_line` and the fourth request for changes are refused the same way, and another reviewer's acceptance lands the work.
  4. The person the playbook routes the decision to never sees it.
- **The rest of item 3:**
  - **Helpers.** Helpers may name human roles and carry `min` (schema `helper`). The spec never says whether `min` gates the owner's exits (spec:451). If it does, dropping a human helper, or the scrum quorum of three estimators (scrum:100), is on the allowlist.
  - **Capacity.** Raising `policy.capacity` lets a `capacity` guard (scrum:87, :123) pass any load. Read literally, that contradicts spec:1203's "a guard".
  - **Goals.** Principle 3 ties nested authority to the goal scope (spec:67), and §7.2 leases "the subtrees it owns" (spec:695). Neither says whether the goal type bounds that scope or those subtrees, yet `policy.goals` is allowlisted.
- **Resolution:**
  - A `wip` change that adds or lowers a limit counting a human-, tool- or process-owned or verification state (`per_state`), or a human role (`per_role`), waits for a person. Raising any limit, and limits that count only production states or the board, stay on the allowlist.
  - Alternatively, a work-in-progress limit never refuses an entry into a human-owned state that a verdict or a loop limit routes to.
  - State whether `helpers.min` gates the owner's exits. If it does, a helpers change that removes a human role or lowers `min` waits.
  - Reword spec:40 and spec:1203 to name what waits: people, tools, approvals, verdicts, verification states, delivery evidence and signed events. Call `wip` and `capacity` throughput limits that the allowlist leaves to agents. State that `policy.goals` bounds no write scope and no lease.

#### V3. Allowlisted links carry no record, so trust.md's chain and "every machine runs the same version in force" fail

- **Type:** internal · **Severity:** major. It concerns the core's use of trust.md.
- **Claim:**
  - spec:187: "The proposed version is the resolved configuration (below) at the head of the default branch".
  - spec:188: "The version in force is the last proposed version that took effect: on commit, when every difference is on the allowlist below, or on a person's confirmation … together with how it took effect — the allowlisted differences, or the confirmation record — so every machine runs the same version".
  - spec:229: "Every machine runs the same version in force, because every machine verifies the same records on the board". Row 32 (spec:1183) says the same.
- **Conflicts with:**
  - trust:109: "Every machine that loads the board verifies the chain of records from the anchor to the version in force".
  - trust:110: "A machine that cannot verify a record keeps running the last version it verified".
  - trust:111: "No machine runs a version that another machine merely claims".
  - trust:105: "a record that names any other replaced version is refused and reported".
  - trust:220: "verifies the record chain back to the anchor. It fails closed".
- **Derivation:**
  1. V0 is in force with a record. Commit C1 adds a production state, which is allowlisted. Machine A's kernel loads at C1 and stores V1 "with the allowlisted differences". Commit C2 lowers a delegation ceiling, which waits.
  2. Machine B's kernel first loads at C2. Whether C1 ever "took effect" depends on whether some kernel loaded while C1 was the head. The version in force is a function of load timing, not of the history.
  3. B finds V1 on the board without a record.
     - Under trust:110 and trust:220 it runs V0, the last version it verified.
     - If it accepts A's stored claim instead, it runs what another machine merely claims (trust:111). An agent that writes a stored version with a false "allowlisted" claim then makes every machine run it.
  4. Alice confirms C2 on A, so the record's replaced digest is V1's. B refuses the record (trust:105) and stays on V0. Row 32's "one confirmation serves every machine" fails.
- **Resolution:**
  - Define the version in force from the history, not from load times. Start at the last record and walk the default branch's first-parent commits, or apply numbers without git.
    - Each commit whose resolved configuration differs from the running one only by allowlisted differences takes effect.
    - The first commit that does not is pending, and so is every later one.
    - Store each allowlisted version's resolved configuration on the board.
  - Every machine re-derives each allowlisted link from the two stored configurations and never accepts a stored claim.
  - trust.md's chain (§4, §12) includes these links, and a record's replaced digest is the derived version in force.
  - spec:1208 should say that item 13 also decides this chain and V9.

#### V4. Capability selectors admit installed role skills whose contributions nothing confirms

- **Type:** authority · **Severity:** major. It is U5's residual, and it bites from PC2.
- **Claim:**
  - spec:450: owners `{ "one_of": { "capability": [...] }, "by": "assignment.role" }` "for every installed role with those capabilities (today's open-ended roles)".
  - schema:1109: "Any installed agent role with one of these capabilities".
  - PC2 row (spec:1117): "task-board resolves roles from the project overlay `.roles` first, then installed role skills, then `~/.roles`".
  - spec:193: the resolved configuration holds "the `data/role.json` contribution … of every role skill the resolved roles bind".
- **Conflicts with:**
  - spec:798: "By default an agent may install an audited skill".
  - spec:715: a role skill whose contribution differs "waits for a person".
  - U5's resolution (spec:1451).
- **Derivation:**
  - A project extends the default, whose `analysis`, `development` and `reviewing` states use capability selectors (default:66, :71, :75).
  - From PC2 an orchestrator installs an audited role skill whose `data/role.json` declares capability `reviewer` and no needs.
  - No role alias binds it, so its contribution is not in the resolved configuration and nothing waits. The selector admits it, the orchestrator assigns it, and it reviews and accepts.
  - The needs of the project's own `reviewer` role never apply, and the capability itself is the skill's own claim.
  - Under the allowlist, re-owning a production state to a producer or analyst selector (V1d) opens the same door on commit.
- **Resolution:** a capability selector ranges over the role aliases of the resolved `roles` map of the version in force, and in legacy mode over the committed `.roles` overlay. It never ranges over installed skills that no alias binds. An installed role skill becomes a role only through an alias, and adding an alias waits. Say so at spec:450, in the PC2 row and in schema:1109.

  - spec:1108: "Legacy mode is the one place where anything is read unconfirmed".
- **Conflicts with:**

  - ops:108, decision 15a: "правила процесса … переезжают в `Playbook.json`".
- **Derivation:**
