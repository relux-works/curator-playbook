The three most important new findings:

1. **N1 (blocking): the authority policy is read from a file any session can edit.** Signature requirements, `people`, `policy.enable` and the hard needs live in the working-tree `Playbook.json`. The kernel reads that file live. The orchestrator's session works in the same checkout, so deleting `policy.signatures` or a `require` takes one edit, with no review and no signature. The board records only the template's digest. waggle solves the same problem for its roster by reading it "at a pinned revision".
2. **N6 (with N5): the decided tool mechanism is replaced by a rule Curator cannot check.** decisions.md:84 has the orchestrator skill's manifest depend on the tool provider in `runtime` mode, narrowed to its exported commands. v2 says instead that "a published template may bind a tool only to a skill of its own package". Curator has no multi-skill package: every skill is its own package and installation unit. Worse, v2's one-selector packaging (`include: ["*"]`) selects the tool skill directly. That makes it a `full` requirement: its context reaches every session and all its commands are active. Tool execution itself is not gated by `policy.enable`, and the project cannot disable a tool, although the same decision says it may.
3. **N10 (with N9): the delivery invariants contradict both examples they govern.** Invariant 3, "review only after a published Change Request revision", holds "whatever the playbook declares". The default admits `* → reviewing` for inline, CR-less work, as today's code does (consistency.go:115-122), so the PC1 target breaks the invariant or the invariant is not unconditional. Separately, dev-cycle's story joins on `children.in: [accepted, done, closed]`, while its design tasks end in `approved`. A story with a design task never integrates, contrary to §6.10's "so it neither deadlocks".

## 3. New findings

### Blocking

#### N1. The authority policy is read from a file any session can edit
- **Type:** authority · **Severity:** blocking · **Decision:** H1
- **Claim:**
  - spec:15: "**Authority stays outside the model.** An agent run never moves work out of a human-owned state, never records a human approval and never posts a tool event. Risky human acts need a waggle approver signature. *decided*"
  - spec:107: `people`, `policy.enable`, `policy.effort_floor` and `policy.signatures` are "Keys that only a project may set".
  - spec:477: a hard requirement is relaxed permanently "only [by] a reviewed change to the project's `Playbook.json`".
  - spec:371: "The board records the resolved template's package identity and semantic digest". This covers the template, not the project file.
- **Conflicts with:**
  - waggle.md:63: "Adding a teammate is a reviewed pull request. Hosts read the roster at a pinned revision."
  - waggle.md:237: layer 1, "Authority outside the model | gates, scope leases, supervisor-executed `cancel`/`halt`, signature policy | yes" (mandatory).
- **Derivation:**
  - The kernel reads `Playbook.json` from the project checkout. The orchestrator's primary session works in that checkout with ordinary file tools.
  - One edit then removes each protection v2 adds:
    - delete `policy.signatures.require_for`, and no human act needs a signature;
    - set `on_unmet: "fallback"` and `policy.enable.relaxations: true`;
    - drop `not_same_publisher_as`, the "permanent" relaxation.
  - Nothing records or checks the project file's digest. The kernel cannot tell a reviewed, merged revision from an unreviewed working-tree edit.
  - The signature policy that §4.2 relies on is therefore inside the model's reach.
- **Resolution:**
  - Name the authority-bearing keys: `people`, `policy.signatures`, `policy.enable`, role `needs` and `on_unmet`, `tools`, `events`.
  - Read them only from a pinned revision whose commit signature the roster verifies, as waggle does for its roster.
  - Record that revision and the project file's resolved digest on the board.
  - Refuse a change to these keys between loads, or require a human signature for it.

### Major

#### N2. waggle has no message type, namespace or principal for board approvals and external events
- **Type:** external-constraint · **Severity:** major · **Decision:** H7
- **Claim:**
  - spec:267: an approval "is a waggle approver signature at the configured assurance".
  - spec:320: "External events enter through `task-board event post <event> --element <id>` with a signed payload"; the signers are `tool:supplier-portal@cafe` and `tool:payment-gateway@cafe` (spec:323; cafe:27-29).
  - spec:279-281: a process on another board is reached through waggle, and "`process.returned` carries the final state of the received element".
  - track.md:37: waggle is a dependency only for "approver signatures for risky human acts, hand-off offers between orchestrators, scope leases".
- **Conflicts with:**
  - waggle.md:55-61: the principals are `op:`, `orch:`, `worker:`, `host:` and a partner `orch:*@partner`. There is no service or `tool:` principal.
  - waggle.md:66-75: roster namespaces are `coord`, `cmd`, `approve.coord`, `approve.cmd`, `endorse.*`, `report` and `receipt`.
  - waggle.md:214-219: the classes are `coord`, `cmd`, `report` and `receipt`, and an approval is a co-signature over one of them (waggle.md:102-110, :139-141). `coord` has `handoff-offer` and `handoff-accept` but no message returning a received element's final state (waggle.md:216).
- **Derivation:**
  - A board approval, a signed human transition, a signed external event and a cross-board `process.returned` have no waggle representation.
  - Verification takes the expected class "from the channel" and checks each signature's namespace against the roster (waggle.md:148-150).
  - A `tool:` signer has no roster kind and no namespace. So a verifier following waggle refuses every signed `payment.received`, or the kernel verifies with rules waggle does not define.
  - v0 F1's resolution item "Specify a waggle message type for board approvals" is still open.
- **Resolution:** file a waggle amendment and list it in track.md Dependencies with the milestone that needs it. It should add:
  - a board class for approvals and signed transitions (`approve.board.v1@waggle`);
  - an event class, with waggle's expiry and de-duplication (waggle.md:152-153);
  - a service principal kind admitted only for that class;
  - a `coord` type that returns a hand-off's result.

#### N3. `policy.signatures` cannot require the one property that shows a person acted
- **Type:** authority · **Severity:** major · **Decision:** H7
- **Claim:**
  - spec:141: "`policy.signatures` (§6.8) names which human acts need a waggle approver signature and at what key assurance (`software`, `hardware-bound`, `attested`, waggle §4.5)".
  - schema:1386-1392 has `min_assurance` only; scrum/project.Playbook.json:25 sets `"min_assurance": "hardware-bound"`.
- **Conflicts with:**
  - waggle.md:181: a FIDO2 signature with user verification "is the only form of 'the operator was physically there' that other people can check. Touch ID prompts … are not visible in the signature, so they do not satisfy this rule."
  - waggle.md:195: assurance describes where the key lives; "A separate per-signature fact, `user_verified`, exists only where the signature format carries it".
  - waggle.md:23 and :406: until CM1, children inherit the parent's manager variables.
- **Derivation:**
  - An agent process running as the operator's OS user that can reach `ssh-agent` gets `software` signatures freely.
  - It gets `hardware-bound` signatures whenever the key does not demand presence for each use.
  - The approval then carries a valid approver signature that no person gave. "Risky human acts need a waggle approver signature" (spec:15) establishes no human act at any `min_assurance`.
- **Resolution:**
  - Add `user_verified: required | if-supported` (waggle.md:208's form) to `policy.signatures`, required by default for approvals, relaxations and halts.
  - State that approvals are signed only through the operator-facing command that renders the payload (waggle.md:140).

#### N4. Templates choose who may sign the events that move work
- **Type:** authority · **Severity:** major · **Decision:** H1
- **Claim:**
  - spec:107 lists the project-only keys: "`people`, `policy.enable`, `policy.effort_floor`, `policy.signatures`, tool bindings to other packages' skills". `events` is not among them.
  - spec:320: "A playbook declares the events it reacts to and who may sign them".
  - The published template `cafe-ops` sets its signers itself (cafe:26-30).
- **Conflicts with:**
  - spec:131, :135-139: human authority comes only from the project's `people` map ("whose members are waggle roster principals").
  - spec:14 and :453: what a package proposes takes effect only when the project enables it.
- **Derivation:**
  - `invoiced → paid on payment.received` (cafe:113) enters the workflow's only success state. The principal whose signature fires it is written into package bytes.
  - Principals carry an organization (`@cafe`). For any other adopter they either match nobody or, if that name exists in the adopter's roster, let a foreign principal move the adopter's work. A project that does not override the map inherits them.
  - The signer is also only the bridge that "receives [a webhook and] posts the signed event" (spec:326). The spec does not require the bridge to authenticate the webhook's sender.
- **Resolution:**
  - A template declares events and a signer group name; the project binds the group to principals, as with `people`.
  - Refuse an event whose signer group the project has not bound.
  - Require the bridge to verify the provider's own webhook authentication before it signs.

#### N5. Tool invocation is a side effect the project can neither gate nor disable
- **Type:** authority · **Severity:** major · **Decision:** H3
- **Claim:**
  - spec:453: "**Side effects are proposals.** Schedules (§6.6), `spawn.owner` actions, and `fallback`/`degrade` relaxations (§9) that a package declares take effect only when the project enables them (`policy.enable`)." Tools are not in the list, and `enable` has only `schedules`, `auto_spawn` and `relaxations` (schema:1333-1360).

- **Claim:**
  - spec:429: "Template names must be unique among installed skills in the effective scope (project before global); two candidates are an error".
  - spec:366: `"package": "relux-works/curator-playbook-dev-cycle@v1.0.0"`, "which the resolver checks against the installed lock".
- **Conflicts with:**
  - manager.md:1011-1012: "Precedence is project, hybrid, global". manager.md:999-1000: the global store's "physical location is implementation-specific".
  - skillfile-sources.md:132-141: a package identity is `{kind:"network-git", repository:<canonical host/path>, commit, directory}`, a `local-snapshot` digest, or `configured-git`.
  - AS §6 (agent-selection.md:119): a reviewer may run in its own Curator profile, whose managed home installs its own skill set.
- **Derivation:**
  - For a project/global pair, precedence and "two candidates are an error" contradict each other, and the hybrid scope is missing.
  - A kernel cannot scan global locations. Two processes on one board in different profiles can see different templates.
  - An `owner/repo@tag` pin names a tag where the lock holds a commit, and it cannot match a `local-snapshot` or `configured-git` member.
- **Resolution:** resolve templates through Curator's locks in the order project, hybrid, global; make ambiguity within one scope an error; pin parents by Curator's package identity.

#### N27. Evidence freshness is undefined
- **Type:** assumption · **Severity:** minor
- **Claim:** spec:258 guards `verdict` (`is`), `approvals` (`role`, `min`) and `outcome.present`. spec:267: "An approval is a board record bound to the approving principal."
- **Conflicts with:** goal_acceptance.go:172-173: today a reviewer verdict counts only if it was recorded after the latest producer outcome.
- **Derivation:** nothing binds evidence to the state entry it gates.
  - After `challenge → hld` on a contradiction, `hld → challenge` passes on the old outcome, and `challenge → hld` can fire again on the stale verdict without a new refutation (dev-cycle:83-84).
  - In §7.1's example, `qa → review` passes on the developer's outcome before the tester writes anything (spec:357).
  - The approval recorded before `approval → sent` still satisfies `escalated → sent` once the SLA fires (cafe:102-105).
- **Resolution:** bind verdicts, approvals and outcomes to the entry or revision the guard evaluates.

#### N28. dev-cycle keeps task classes that cannot reach `done`
- **Type:** internal · **Severity:** minor
- **Claim:** dev-cycle:48: `task_class` takes `code`, `metadata`, `docs` and `research`.
- **Conflicts with:** a dev task reaches review only with `delivery.cr-published`, and done only on `delivery.integrated` (dev-cycle:136, :147-148). Today `metadata` and `research` work is CR-less inline work (consistency.go:115-122; landed_methods.go:553-565).
- **Derivation:** a `metadata` or `research` dev task without a Change Request can only be closed.
- **Resolution:** limit dev-task classes to Change Request work, or add the inline route guarded by `delivery.cr-absent`.

#### N29. The schema accepts what §10 says it refuses, and is silent where the spec requires
- **Type:** internal · **Severity:** minor
- **Claim:** spec:515: "the schema refuses program strings, URLs, effort needs, tools posing as reviewers and action objects inside guards". spec:218: "Each element has exactly one owner in each state".
- **Conflicts with (probe documents in the scratchpad):**

The relevant schema lines are :1562-1576, :1497-1504, :1205-1210 and :45-48.
  - A non-terminal state with no owner validates (schema:939-1012).
  - The descriptions still key `via` and `remove` on the from–to pair (schema:1072, :1117), while the spec keys on `(from, to, via)` (spec:246, :368).
- **Resolution:**
  - Narrow the claim to tool bindings.
  - Give each hook an argument schema with `additionalProperties: false` (F26's open item).
  - Have the validator require an owner on resolved non-terminal states.
  - Fix the two descriptions.

#### N30. Without Curator, tools still run; the decision says they may not
- **Type:** decision-conflict · **Severity:** minor · **Decision:** H3
- **Claim:** spec:440: "tool commands of unaudited skills run only when the operator confirms them".
- **Conflicts with:** decisions.md:84: "the kernel runs only commands exported by skills installed through Curator".
- **Resolution:** refuse tool bindings to skills that Curator did not install, or have the operator amend the decision.

#### N31. Reopen transitions leave ownerless states, with no rule for who may fire them
- **Type:** authority · **Severity:** minor
- **Claim:** spec:222: "`terminal` states have no owner. Leaving one needs a transition marked `reopen: true`". spec:130-133 define authority by the owner kind of the source state.
- **Conflicts with:** dev-cycle:200: `accepted → superseded` (`reopen: true`) on a `decision`, part of the refuter's memory (spec:543, :548); spec:15.
- **Derivation:** the source state is terminal and has no owner, so §4.2 says nothing about who may fire the transition. Any actor, an agent run included, can supersede a human decision once `links` is set.
- **Resolution:** give reopen transitions an explicit actor rule, for example a human for types whose initial state is human-owned.

#### N32. The guard-bypass check is undefined, and under its only example it fails two examples
- **Type:** internal · **Severity:** minor
- **Claim:**
  - spec:510: "`workflow purchase: escalated → sent skips the approvals guard of approval → sent`".
  - spec:515 lists the checks the prototype ran; guard bypass is not among them, yet "every v2 example passes".
- **Derivation:** read as "a transition into a state lacks a guard that another transition into that state carries", the check flags:
  - dev-cycle: `review → development` and `escalated → development` skip the `blockers.clear`, `estimate` and `assignee` of `open → development` (dev-cycle:132, :141-150);
  - the default: the integration exits into `done` skip the `blockers.clear`, `delivery.cr-absent` and `delivery.commit-acknowledged` of the inline route (default:124-142).
- **Resolution:** define the rule (for example, authority guards such as `approvals` and `verdict` on every path into a state that one path protects with them), then run it.

#### N33. Automatic transitions lose events that arrive in another state
- **Type:** assumption · **Severity:** minor
- **Claim:** spec:248: "`on` makes the transition automatic: on an `event` or `after` a duration in the source state."
- **Conflicts with (the examples):**
  - Cafe (cafe:103-105): a supplier confirmation that arrives after the order moved to `escalated` matches no transition and is lost. When the manager sends again, the order waits for a confirmation that already came, and escalates again.
  - prove2me (prove2me:65-72): an attempt accepted while its milestone is `stalled` fires `children.changed` in `stalled`. After `stalled → open` nothing re-evaluates the join, so the milestone stays `open`.
- **Resolution:** define whether events are retained per element or guards are re-evaluated on entry, and what happens to an event that no transition matches.

## 6. Verdict

`human-decision-needed`.

v2 closes most of v0. The default now passes the spec's own portable checks; `via`, creation, hand-off, composition and resolutions are defined; the lookup order and the namespacing follow the record.

Its new authority model does not yet hold together:

- the policy that grants authority sits in a file the model can edit (N1);
- waggle has no message for the approvals and events it relies on (N2);
- its signatures cannot show that a person acted (N3);
- templates still grant event authority and run tools without project enablement (N4, N5);
- the decided Curator mechanism for tools is replaced by one Curator cannot check (N6).

The delivery invariants, v2's answer to v0's deadlock, contradict both examples they govern (N9, N10). The early demos depend on later milestones (N11). Portability regresses through a committed effort floor, binding-based independence and an automatic selection without admission (N13, N14, N16).

Eight decisions (H1–H8) belong to a person. The rest can be corrected in the draft before the `challenge` state runs again.
